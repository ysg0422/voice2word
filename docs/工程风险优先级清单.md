## P0 —— 建议本轮处理

### P0-1 数据库自愈把瞬时错误当成损坏

`heal_if_corrupt`（`src/storage/db.rs:380`）的判据是：

```rust
let healthy = conn.query_row("PRAGMA quick_check", [], ...)
    .map(|s| s == "ok")
    .unwrap_or(false);
```

`quick_check` 返回 `Err` 的原因不止"库损坏"：BUSY、IO 错误、杀毒软件临时锁文件都会走到这里，而 `unwrap_or(false)` 把它们一视同仁。后果是**改名现有库 + 新建空库**：数据其实在 `*.corrupt-<时间戳>.db` 里，但用户看到的是"历史记录全没了"，且提示只落在日志（`:395`），UI 无感知。

建议：
1. 区分 `Err(_)` 与 `Ok("ok" 以外的内容)`：前者重试一次（例如 2 次 200ms），仍失败就**放行**并记 warn；只有真正的完整性错误才自愈。
2. 自愈发生时通过现有错误横幅通道告知用户"已备份到 xxx"，而不是只写日志。
3. 给 `heal_if_corrupt` 补两个测试：可注入的瞬时错误不应触发改名；真损坏时改名并新建。

### P0-2 配音取消不生效

`run_dub_inner`（`src/core/dub_flow.rs:189`）只在阶段之间检查 `cancel`（`:264`、`:274`），而第一遍批量合成 `tts.synthesize_batch(&items, ...)`（`:253`）拿不到取消位。TTS 的总预算按 `60 + 6s/句`、封顶 2 小时（见引擎侧超时设置），联网合成时用户点取消要等整批跑完。

建议：
- `synthesize_batch` / runner 协议加取消通道（按句轮询一个 `AtomicBool` 即可，runner 已经是逐句调用）；
- 至少把批量切成小批（如 20 句一批），批间检查取消位，代价远小于改协议；
- 顺手核对 `DubShared` 的 `cancel` 与 `TaskPipeline::cancel` 是否共用同一语义（目前配音走 UI 专用取消位）。

## P1 —— 兼容性与一致性

### P1-1 工程格式硬编码 30fps / 1920×1080

- `fcpxml.rs:43`：`FFVideoFormat1080p30` + `frameDuration="1/30s"` + 1920×1080
- `premiere.rs:34`：`let fps = 30.0;`，帧号按 `round`
- `jianying.rs:439/542/570`：1920、`fps: 30.0`

非 30fps / 非 1080p 素材导入剪辑软件后会出现帧量化漂移和画布不符；FCPXML 用三位小数秒而非帧对齐有理数（1001/30000s），FCP 可能拒绝或重算。另外 FCPXML / Premiere 不写素材轨（无 `<file>`），工程必须手动补视频。

建议：导出时探测源媒体帧率/分辨率（ffprobe 已封装在 `FFmpegEngine`），缺省才回退 30/1080p；FCPXML 改用 `1001/30000s` 这类有理数。工作量中等，但属于"导出到专业软件"的信任底线。

### P1-2 JSON 导出/导入字段不对称

`json.rs:42-56` 导出字段：`index/start/end/duration/text/raw_text/translation/translation_lang/language/confidence/speaker/words/speaker_label`。
`reader.rs:583-595` 的 `JsonSegmentIn` **不包含** `speaker_label`，也整份丢失 `Segment.locked`、`Segment.translations`（多语言包）、`Segment.speaker_name`。

`reader.rs:488-497` 的注释已说明 `polished` 的丢失是"有意接受"，这点没问题；但 `locked` 与 `translations` 属于用户编辑状态，往返一次就没了。如果 JSON 定位只是"导出给外部工具"，可以接受——**建议在文档里写明"JSON 不是工程存档格式"**；如果希望往返无损，补四个字段即可。

### P1-3 zip 解压不可取消、整包读入内存

`model_download.rs:2256-2261`：

```rust
let bytes = fs::read(part)?;
zip_extract::extract_zip(&bytes, dir)?;
```

tar.bz2 分支已经支持取消（`:2254`），zip 分支没有，且 `fs::read` 把整个包读进内存。模型包几百 MB 时取消无效、峰值内存翻倍。

建议：`extract_zip` 改为接收 `&mut impl Read + Seek`（zip crate 支持流式），每解一个条目检查一次取消位。与 tar 分支对齐。

### P1-4 阶段看板漏两个阶段

`pipeline.rs:257` 的 `Stage` 枚举与 `Stage::ALL` 只有 7 项，但管线还发了两条字符串字面量：

- `:1982` `StageChanged("人声分离")`
- `:2730` `StageChanged("说话人分离")`

UI 的步骤看板按 `Stage::ALL` 渲染，这两个阶段不显示，进度会"跳格"。修复：枚举补两项（或在文档中明确它们是"可选阶段、不进看板"并改渲染逻辑），两处字面量改成 `Stage::X.label()`。

### P1-5 被跟踪的 config.toml 是开发机配置

`config.toml` 在 git 中（`git ls-files` 可证），且内容是开发机现状：

- `:4` `whisper_model = "models/sensevoice/model.int8.onnx"`（whisper 的模型路径指向 SenseVoice 的 onnx）
- `:17` `enable_polish = true`
- `:72` `mode = "offline_qwen"`（翻译默认走本机 LLM）、`:78` `target_lang = "日本語"`

release 包用 `--print-default-config` 重新生成，但**源码运行、测试、Skill 文档**直接吃这份文件，于是出现"代码默认值 / config.toml / 文档"三份说法。`config.local.toml` 已正确 gitignore，说明分层机制在，只是根配置没有收敛成中性默认值。

建议：把 `config.toml` 重置为中性默认（不指向任何本机模型），开发机差异全部放 `config.local.toml`；加一个测试断言"仓库内 config.toml 与 `--print-default-config` 输出一致"（CI 里已有类似 packaging 校验，可挂进去）。

### P1-6 文档与集成契约漂移

已核实的四处：

| 位置 | 现状 | 实际 |
|---|---|---|
| `docs/headless.md:217` | 示例版本 `0.2.0` | `Cargo.toml` 为 `0.2.26` |
| `integrations/voice2word-skill/SKILL.md:110` | 称示例配置 `enable_polish=false` | `config.toml:17` 为 `true` |

MCP 仍只暴露 `transcribe/probe/version`（`voice2word_mcp.py:349-407`），Skill 脚本参数也更窄。CLI 已经领先集成层一个版本。

## P2 —— 工程卫生与性能（可排期）

### P2-1 切块部分失败仍返回成功（有意设计，需产品确认）

`chunked_whisper.rs:712-783`：单块失败只 warn 并记录缺失区间，最终仍 `Ok(...)`；进度文案里会带"（N 个切块失败，缺失约 Xs）"。设计理由（`:652-655` 注释）是避免"任何一块出错就一条字幕都没有"，合理。但上层 UI 没有把"缺失区间"升级成显式警告，用户可能拿到缺 1–2 分钟字幕的"成功"结果。建议在完成弹窗/历史库里带上这个标记。
