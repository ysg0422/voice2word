## 四、今天修好的缺陷（5 个）

### 4.1 时间轴被按倍速缩放两遍 —— `src/core/pipeline.rs`（最严重）

- `can_stream` 分支内对返回片段调了一次 `scale_segment_to_original_time`，分支之后的汇总处 `restorer.restore_all()` 又缩了一次。
- **默认配置即可命中**：`preprocess_enabled` 默认 true、`preprocess_compact` 默认 false（只做增强）→ `prep_active=true`；用户把音频加速调成 >1.0 时 `can_stream=true`。两者叠加，字幕按 **speed²** 定位。
- 后果：1.25 倍时 24 分钟处的字幕跑到 37.5 分钟，越往后越偏，片尾全被钳到总时长。同一条错误时间轴还污染置信度救场的时间窗和说话人分离。
- 修法：删掉分支内那次缩放，新增唯一入口 `restore_final_timeline()`；SenseVoice 分支跳过（它的推流恒为 1.0 倍速）。
- 验证：注入二次缩放后 `final_timeline_restore_scales_exactly_once` FAILED，报 40s→62.5s（= 40×1.25²）；还原后通过。

### 4.2 救场阶段实时预览缺窗口偏移 —— `src/core/pipeline.rs`

- 救场窗口的模型时间轴以窗口起点为 0，预览直接把相对时间推给界面，时间徽章显示成 `00:0x`（真实位置可能在 25 分钟处）。最终 SRT 不受影响。
- 修法：抽出 `shift_window_to_media_timeline()`，预览与回写共用同一次平移。
- 说明：调用点在 async 管线闭包内、无法单测，靠共享函数 + 代码审查确认（已如实标注）。

### 4.3 预览音频馈送子进程泄漏 —— `src/engines/video_player.rs`

- `play()` 里 ffplay spawn 失败时直接丢掉还在运行的 ffmpeg feeder，留下阻塞在满管道上、占着视频文件句柄的孤儿进程；反复预览会累积，导致改名/删除视频失败。
- 修法：启动失败时就地 `kill()+wait()`。可达性低（ffplay 路径已前置检查过）。

### 4.4 `optimize_segments` 非幂等，字幕被静默吞掉 —— `src/subtitle/segment.rs`

- 消重叠把前句尾部收到 `start + 0.1`，压出 0.1 s 碎条；该碎条满足鬼影判据，但判据检查那一步已跑过，本次不删、**下次载入才删**。每次载入工程都会再跑一遍，于是「同一工程打开一次 2 条、再打开变 1 条」，消失的文本无处找回。
- 修法：判据抽成 `should_drop_segment`，末尾 `drop_invalid_and_ghosts_until_stable` 复扫到稳定。
- **触发面窄**（如实标注）：用 Python 复刻边界逻辑跑四个真实全片 JSON（5151 条原始片段），修复前后输出逐条相同、真实数据本来就幂等。属性成立、代码路径成立、真实素材未触发。

### 4.5 换工程后撤销栈未清空 —— `src/app/state.rs` + `src/ui/actions.rs`（数据丢失级）

- `undo_stack` / `redo_stack` 只在构造时初始化，凡整体替换 `segments` 的地方都不清理。`restore_snapshot` 会把快照的 `segments` 赋回并按**当前**工程的 `active_task_id` 写库。
- 后果：打开工程 A 编辑过 → 切到工程 B → 按一次 Ctrl+Z，**A 的整份字幕出现在 B 里并立刻以 B 的 id 写进数据库**，覆盖 B 的历史记录。Ctrl+Z 是全局快捷键，任何页面可触发；清空工作区后按 Ctrl+Z 还会让无对应工程的片段列表复活。
- 修法：新增 `AppState::reset_edit_history()`，在 `load_task_with`、`clear_current_workspace`、`load_from_cache`、`ui/actions.rs` 转写完成处四处调用。

## 七、两条环境级发现

### 7.1 release 构建曾被 fxc 阻塞 —— 根因已修正为「SDK 装在 D 盘且不在 PATH」

- 昨晚判断「本机没有 `fxc.exe`」**不准确**。它装在 `D:\Windows Kits\10\bin\10.0.26100.0\x64\fxc.exe`（注册表 `KitsRoot10 = D:\Windows Kits\10\` 可证）。
- 真因：gpui 0.2.2 的 build script (`build.rs:356`) 只查三处——`GPUI_FXC_PATH` 环境变量、`where.exe fxc.exe`、硬编码的 `C:\Program Files (x86)\Windows Kits\10\bin\10.0.26100.0\x64\fxc.exe`——三项全灭就 panic。**它不读注册表 `KitsRoot10`，而 `embed-resource` 读**，所以同机 rc 找得到、fxc 找不到。
- 另：只有 release 才编译着色器（`#[cfg(not(debug_assertions))] compile_shaders()`），debug 走运行时 `D3DCompileFromFile`，这就是「debug 能过、release 不能过」的原因。
- **已实测修复**：设 `$env:GPUI_FXC_PATH = "D:\Windows Kits\10\bin\10.0.26100.0\x64\fxc.exe"` 后 `cargo build --release` 成功，218 秒产出 `D:\cargo-target\voice2word\release\voice2word.exe`（24,190,464 字节），着色器字节数组是合法 DXBC（魔数 68 88 66 67）。
- `dxc` **不能**替代 fxc（产出 DXIL/SM6，D3D11 不收，且输出头格式不匹配），已实测排除。
- 未做：从零（干净 target）的完整 release 构建；release 二进制的启动冒烟测试。

### 7.2 CPU 吞吐今天比昨晚慢约 36%

同参数、同素材的 CPU 对照：墙钟 268.75 s 对昨晚 197.40 s，但句数、编辑距离、编码次数、解码 token、**输出 SRT 的 SHA256 全部相同**。

**结论：CER 不受影响，但 CPU 墙钟不可跨会话比较**；本轮内噪声地板约 ±5%（默认档与 `--no-compact` 输入输出都相同，墙钟却差 4.8%）。GPU 侧影响小，`-ac 1500` 今天反而快 11%。推测与另一条工作线在跑有关（`%TEMP%\v2w_audio_prep_test` 今天时间戳被更新过）。
